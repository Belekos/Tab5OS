# Vérification indépendante du profilage UI — 0.8.42

`Tab5UiDiagnostics.cpp` et ses interfaces de production ont été compilés sans modification dans un exécutable hôte. Seules les frontières SDK (horloge monotone, raison de reset, attribution d'activité d'affichage) sont simulées. Le test inclut directement l'unité de production afin d'injecter des corruptions dans les octets retenus sans ajouter de branche de test au firmware.

Résultat : **967 vérifications réussies**, AddressSanitizer et UndefinedBehaviorSanitizer actifs. Rapport et empreintes : `tools/verification/ui-diagnostics-0842.json`. Compilation exacte ESP32-P4 réussie sans avertissement : `tools/verification/ui-diagnostics-target-0842.json`.

Cas vérifiés : aucun appel à l'horloge lorsque désactivé ; attribution d'affichage conservée ; seuil inclusif de 20 ms ; compteurs de tous les appels et événements lents, mais au plus un événement retenu par phase et par seconde ; générations d'activation et scopes chevauchant une réactivation ; séparation du travail actif d'une boucle et de l'intervalle entre débuts de boucle ; rotation des huit événements ; sorties bornées jusqu'aux très petites capacités, sans découper UTF-8 ni une ligne ; tous les resets acceptés et les resets froid/brownout/inconnus ; rejet des corruptions de magic, nombre, index, phase et checksum ; durée totale 64 bits et saturation des maxima 32 bits.

L'objet cible confirme **216 octets RTC** pour les deux journaux. Les symboles BSS totalisent **578 octets avant padding du linker** (416 statistiques, 136 limites temporelles par phase, 26 état). Le plus grand cadre local GCC est 224 octets pour le formateur `recent()` ; ce n'est pas la profondeur cumulée de pile. Aucun tableau dynamique, tâche, timer, accès Flash ou SD n'est ajouté par ce module.

Limites : le temps mesuré est une durée murale incluant préemption et attente, pas une consommation CPU. La rétention RTC après reset physique n'a pas été testée. Le checksum détecte une incohérence mais ne garantit pas la persistance lors d'une perte d'alimentation ; les resets jugés non fiables effacent volontairement ce seul journal de diagnostic, jamais les données utilisateur. LeakSanitizer est indisponible dans cet environnement en raison des restrictions ptrace/proc ; aucun résultat LSan n'est revendiqué.

Reproduction : `python3 tools/ui-diagnostics-tests-0842/run.py --build /chemin/temporaire`. Pour le matériel, activer temporairement le profilage, reproduire le lag, relever les phases et l'intervalle maximal, puis désactiver. Ne pas transformer la consultation des piles ou des plus grands blocs en mesure permanente.
